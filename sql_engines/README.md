# SQL across engines: PostgreSQL, MySQL, SQL Server and SQLite

One relational suite, run unchanged against four engines. A small shop schema (products
and orders, [`app/models.py`](app/models.py)) is created by Alembic migrations, and an
HTTP endpoint places orders ([`app/api.py`](app/api.py)).

```bash
uv run pytest sql_engines -m sqlite     # no Docker needed
uv run pytest sql_engines -m postgres   # PostgreSQL 18 in a container
uv run pytest sql_engines -m mysql      # MySQL 8.4
uv run pytest sql_engines -m mssql      # SQL Server 2022 (Developer edition)
uv run pytest sql_engines               # all four
```

## How the engines are wired

- [`tests/conftest.py`](tests/conftest.py): the `sql` fixture is parametrized by engine,
  and each param carries a pytest marker. Every test runs once per engine, and
  `-m postgres` selects one leg. CI runs one job per engine, and Allure labels each result
  with its engine (suite "PostgreSQL 18", tag `postgres`).
- [`tests/servers.py`](tests/servers.py): starts PostgreSQL, MySQL and SQL Server with
  testcontainers (images pinned to exact tags); SQLite is a file in a temp directory.
  Passwords are generated per run and never committed.
- **Per-test isolation:** the `db` fixture opens a transaction and always rolls it back.
  ORM sessions join it with `join_transaction_mode="create_savepoint"`, so code under
  test can `commit()` and the test still leaves nothing behind. Tests that need two real
  connections (locking) use committed rows with unique keys and delete them afterwards.
- **SQL Server on CI:** the image is pulled in a separate CI step, so the pull time
  doesn't count against test timeouts. Start-up uses a health check
  (`sqlcmd SELECT 1` inside the container) and then a connection retry of up to 180 s.
  Only the first connection is retried; tests never are. On GitHub's runners it has
  been ready in well under a minute.

## What it covers

| | PostgreSQL | MySQL | SQL Server | SQLite |
|---|:-:|:-:|:-:|:-:|
| Migrations up / down / up, and an upgrade over existing rows | ✓ | ✓ | ✓ | ✓ (batch mode) |
| ORM models match the migrated schema (Alembic `compare_metadata`) | ✓ | ✓ | ✓ | ✓ |
| NOT NULL, UNIQUE, FOREIGN KEY, CHECK | ✓ | ✓ | ✓ | ✓ |
| Rollback undoes every statement | ✓ | ✓ | ✓ | ✓ |
| Lost update without locking (outcome per engine) | lost | lost | lost | blocked |
| Row lock with `SELECT ... FOR UPDATE` / `UPDLOCK` | ✓ | ✓ | ✓ | skip: no row locks |
| Database-wide write lock (`BEGIN IMMEDIATE`) | skip | skip | skip | ✓ |
| Optimistic locking with a version column | ✓ | ✓ | ✓ | ✓ |
| ORM query equals hand-written SQL and known values | ✓ | ✓ | ✓ | ✓ |
| API writes, test reads the rows back | ✓ | ✓ | ✓ | ✓ |
| Engine differences (below) | ✓ | ✓ | ✓ | ✓ |

**Cost:** SQLite about 1 s. Each container engine is under a minute in CI, including
start-up.

## Engine differences, written down as tests

[`tests/test_engine_differences.py`](tests/test_engine_differences.py) states each
expected behavior in a per-engine dict, so the difference is visible in the code and
proven by CI. Engine-specific features are skipped elsewhere with a reason, never hidden.

| Behavior | PostgreSQL | MySQL | SQL Server | SQLite |
|---|---|---|---|---|
| Default isolation | READ COMMITTED | REPEATABLE READ | READ COMMITTED (locking) | SERIALIZABLE |
| Plain read of a row another transaction changed but hasn't committed | old value | old value | **blocks** | old value |
| SNAPSHOT isolation (opt-in `ALLOW_SNAPSHOT_ISOLATION`) | n/a | n/a | old value, no block | n/a |
| `'Case-1' = 'case-1'` by default | false | **true** | **true** | false |
| UNIQUE treats `Case-1` and `CASE-1` as duplicates | no | **yes** | **yes** | no |
| Type for `Unicode(100)` | VARCHAR | VARCHAR | **NVARCHAR** (VARCHAR turns `李` into `?`) | VARCHAR |
| `.limit(2)` | LIMIT | LIMIT | **TOP** | LIMIT |
| Identity column | GENERATED BY DEFAULT AS IDENTITY | AUTO_INCREMENT | IDENTITY | rowid alias |
| Insert an explicit id in plain SQL | allowed (sequence not advanced) | allowed | **refused** without `IDENTITY_INSERT` | allowed |
| Upsert | `ON CONFLICT` | `ON DUPLICATE KEY UPDATE` | `MERGE` | `ON CONFLICT` |
| `with_for_update()` in SQLAlchemy | FOR UPDATE | FOR UPDATE | **dropped silently**; use `UPDLOCK` | dropped (no row locks) |
| CHECK violation error class (driver) | IntegrityError | **OperationalError** (PyMySQL) | IntegrityError | IntegrityError |
| Text `'abc'` into an INTEGER column | rejected | rejected (strict mode) | rejected | **stored** (type affinity) |
| Foreign keys enforced | always | always | always | **only with `PRAGMA foreign_keys = ON`** |

Two of these were found by the tests rather than planned:

- **`with_for_update()` is a no-op on SQL Server** in SQLAlchemy, with no warning. Without
  the `WITH (UPDLOCK, ROWLOCK)` hint in [`app/repository.py`](app/repository.py), the
  order endpoint would be open to lost updates on SQL Server only.
- **SQLAlchemy turns on `IDENTITY_INSERT` for you** when a Core insert has an explicit id.
  The first version of the identity test used `sa.insert()` and "did not raise"; plain
  SQL shows SQL Server's real behavior.

## What's different about testing each engine

- **PostgreSQL:** the strictest about types and the most standard. An error aborts the
  whole transaction until a rollback, so every negative test runs inside a SAVEPOINT.
  Explicit ids don't advance identity sequences.
- **MySQL:** case-insensitive comparisons and uniqueness by default (collation),
  REPEATABLE READ by default, DDL that commits implicitly, and CHECK constraints that
  were ignored before 8.0.16. Driver error classes differ from other engines.
- **SQL Server:** locking READ COMMITTED means readers wait for writers unless snapshot
  isolation is turned on; NVARCHAR for Unicode; TOP, MERGE, IDENTITY. Slowest to start,
  and needs about 2 GB of RAM. The free Developer edition image is used.
- **SQLite:** a file, not a server. One writer at a time for the whole database, so
  concurrency tests behave differently. Flexible typing, and foreign keys off unless
  enabled per connection. Python's driver needs SQLAlchemy's transaction recipe for
  SAVEPOINTs to work ([`app/database.py`](app/database.py)). Great for fast tests, but
  its passing tests prove little about the other three, which is why this suite runs on
  all four.
